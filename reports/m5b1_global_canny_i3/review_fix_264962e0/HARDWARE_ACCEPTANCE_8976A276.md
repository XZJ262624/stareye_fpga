## 准备与执行

1. 沿用已验证M5A板卡、供电、显示和相机连接。与M5B.0R诊断不同，本轮需要接回AR0135；断电时完成连接，不用带电拔插模拟故障。
2. 用户已确认使用已有板载USB串口。使用其现有接口，不改FPGA管脚；工程uart_tx_o为1.8V。若这个USB口无法接收SM5B数据，反馈端口与现象，先确认物理路由，不自行猜接外部TTL。
3. 在串口接收软件选择该板卡COM口、460800、8数据位、无校验、1停止位、无流控。开启**接收原始二进制文件**保存，不用文本日志替代，不做换行/编码转换，也不要只保存终端显示。记录COM、软件、参数及二进制路径。
4. 在JTAG配置前开始记录，再由用户下载指定bit；记录Programmer结果及时间。单次导出发生在冷启动后首个成功job，晚开记录可能错过分类/结果。如错过，不按普通reset重试；先反馈，必要时重新冷配置并从前开始记录。
5. 先观察启动约1分钟：显示器是否识别1280×720@60Hz，相机画面/默认BIN是否更新、LED校准及故障状态、是否收到串口数据。若黑屏、校准失败、RT故障/硬停，先停止本轮验收并保留记录，不反复尝试热恢复。
6. 保持串口持续保存，连续运行至少30分钟。分别测试静态高对比场景（文字/直边）和运动场景，记录时间与对应现象。至少轮询七模式一遍：RAW/MAG/BIN/OVR/NMS/CNY/COV；同时按两键再松开循环模式，单独按第一/第二键再松开增加/减少阈值16，沿用M5A按键语义。记录OSD模式和阈值，无黑屏、闪屏、花屏、冻结、明显错列/撕裂及新增RT错误。
7. 结束后保存完整二进制、显示和LED记录，反馈路径给Work。用户不必自行解析统计；Work用当前m5b1_uart_decode.py离线解包并与软件BFS逐bit比对。

## LED解释（RTL位序；以板卡实际亮灭极性记录）

用户以指定M0镜像断开相机验证启动顺序后，已对应照片方向：从左到右为逻辑LED7、6、5、4、3、2、1、0。M5B只将逻辑0~5用作状态；左起两颗7/6与相机脚共享，不作为状态判断。资料与M0取反接线为低电平亮：故障灯4/5无故障时亮、故障有效时灭，校准灯1成功后灭；LED2忙时灭、闲时亮。不得将“亮”直接等同逻辑1。

| LED | 含义 | 记录要求 |
|---|---|---|
| 0 | UI heartbeat | 持续变化；记录闪烁或停止 |
| 1 | cal_done && cal_pass | 完成校准后保持有效；记录丢失 |
| 2 | job_busy | 记录变化，不以常亮/常灭单独判失败 |
| 3 | 每次成功发布翻转 | 记录是否观察到变化；最终次数以UART published为准 |
| 4 | 视频FIFO故障或quarantine或stop | 正常验收不应出现；出现即保留记录并停止 |
| 5 | BG sticky fault | 记录首次时间；算法/捕获超时也可能置位，须由UART区分，不凭此单独判定硬件损坏或PASS |

## Work收到实测后的判定项

- 镜像绑定、JTAG方式、AR0135连接及Programmer结果完整。
- 至少30分钟720p60/相机运动更新与七模式共存观察，无新增实时故障、校准丢失或重启。
- 原始UART可校验完整包CRC；首个成功job包含同身份的1280×720分类230400B与结果115200B，capture_success有效，软件BFS逐bit一致。只有统计或截断导出不能记为此项PASS；解包重同步跳过的数据须显式记录。
- 统计检查真实B/R响应、ID/LAST/范围/epoch/watchdog、FIFO错误与calibration/quarantine；正常实测这些错误须为0。真实ID校验通过是该实测事务范围的证据，不代替加密DDR内部或所有ID的形式证明。
- 汇总requests/accepted/capture_drop/published、pair/scan/elapsed、local cancellations及成功/超时率、有效发布率、各客户端最大wait/service和水位。4us仅离线模型，实测服务量由Work核对；不承诺1~2fps。允许设计规定的安全不发布超时，但不能把零成功发布说成全局功能PASS。
- 记录BG故障的具体统计原因。任何RT错误、quarantine、校准丢失、CRC/BFS不一致或硬停，整体验收不能直接PASS，交Work分析。
- 本次不执行warm reset/热恢复测试、不故意注入DDR协议卡死，不改变电压/温度做PVT测试。它们继续PENDING；硬停仅冷重新配置恢复的限制不因此解除。
