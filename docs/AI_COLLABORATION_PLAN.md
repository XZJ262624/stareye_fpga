# “星眸”AI 多模型协作与交接方案

版本：V1.0  
适用项目：2026 全国大学生嵌入式芯片与系统设计竞赛 FPGA 赛道——“星眸多算子边缘感知系统”  
目标平台：易灵思 VF-Ti60F225  
当前技术路线：摄像头采集 → 灰度化 → 滤波 → 边缘检测 → HDMI 显示；后续扩展多算子切换、自适应阈值、彩色叠加、OSD、延迟与资源测试。

## 一、总原则

采用“一个项目、三个模型角色、一个事实源、一个写入者”的方式。

1. 所有对话都放入独立项目“嵌赛2026｜星眸FPGA”。
2. 不同模型使用不同对话，但读取同一套项目文件。
3. 任何时刻只允许一个工程会话修改主线代码，其他模型只解释或审查，防止互相覆盖。
4. 模型之间不依赖“记住上一段聊天”，而是通过项目文件交接。
5. 工程按可验证里程碑推进，不允许一次生成完整系统后再统一调试。
6. 仿真、综合、时序报告和上板现象优先于模型判断；没有验证证据的代码只能算“候选实现”。

## 二、模型角色分工

| 角色 | 推荐模型与档位 | 主要职责 | 是否修改工程 |
| --- | --- | --- | --- |
| 操作教练 | Luna 或 Sol，Low/Medium | 解释 FPGA/Verilog 概念；告诉用户下一步点击、输入什么命令；解释简单错误；把复杂步骤拆小 | 默认不修改，只指导 |
| 主线工程师 | GPT-6.1 Sol，Medium；必要时 High/Extra High | 日常 RTL、Testbench、约束、脚本、仿真与文档维护；持续迭代 | 是，主写入者 |
| 总架构师/疑难专家 | GPT-6 Astra，Medium；关键难题用 Extra High | 架构冻结、接口设计、跨模块联调、时钟域/复位/流水线延迟、复杂故障、资源与时序优化、最终审查 | 仅在明确接管某个里程碑时修改 |

推荐工作量分配：操作教练约 25%，Sol 主线工程师约 60%，Astra 约 15%。Astra 应用于关键节点，而不是每一步操作。

### 何时升级到 Astra

满足任一条件就升级：

- 同时涉及三个以上模块或接口；
- 涉及像素时序、行场同步、跨时钟域、复位、DDR/缓存或流水线延迟对齐；
- 同一个问题经过两轮修改仍未解决；
- 需要改变已经确定的系统架构或模块接口；
- 综合能够通过，但时序不收敛、资源异常或上板现象与仿真不一致；
- 进入阶段评审、性能优化或最终代码审查。

问题解决、接口确定后，由 Sol 接回日常实现和迭代。

## 三、项目阶段与模型安排

| 阶段 | 主要工作 | 主模型 | Astra 介入点 | 用户必须完成的验证 |
| --- | --- | --- | --- | --- |
| P0 背景与需求冻结 | 整理赛题、板卡、摄像头、显示接口、目标指标 | Sol | 审查总体路线与风险 | 确认硬件清单和演示目标 |
| M0 开发环境与点灯 | 安装 Efinity、创建工程、管脚约束、下载程序、LED/时钟验证 | 操作教练 + Sol | 通常不需要 | 板卡能稳定下载并运行 |
| M1 视频直通 | 摄像头初始化/采集、测试图或原始画面、HDMI 输出 | Sol | 冻结像素流接口、时钟与同步方案 | 显示稳定、分辨率正确、无明显撕裂 |
| M2 灰度化 | RGB/YUV 转灰度、延迟对齐、旁路切换 | Sol | 审查定点系数和接口延迟 | 仿真像素正确，上板可切换原图/灰度 |
| M3 3×3 窗口与滤波 | 行缓存、窗口生成、中值或均值滤波 | Sol | 设计行缓存与边界策略 | 仿真覆盖首行、末行和边界像素 |
| M4 边缘检测 | Sobel、多算子、阈值分割 | Sol | 审查流水线、位宽和算子统一接口 | 仿真参考值一致，上板边缘稳定 |
| M5 功能扩展 | 算子切换、自适应阈值、彩色叠加、OSD | Sol | 审查功能组合和演示价值 | 每项功能可独立开关并回退 |
| M6 优化与封版 | 时序收敛、资源/延迟/帧率统计、长时间稳定性 | Astra + Sol | Astra 主导诊断和最终审查 | 保存综合、时序、资源和实测证据 |
| M7 参赛材料 | 报告、PPT、视频脚本、创新点与答辩问题 | Sol | Astra 做最终逻辑审查 | 材料指标与真实工程一致 |

## 四、统一项目文件

建议实际工程目录如下：

```text
StarEye/
├─ AGENTS.md
├─ README.md
├─ docs/
│  ├─ PROJECT_BRIEF.md
│  ├─ MILESTONES.md
│  ├─ STATUS.md
│  ├─ HANDOFF.md
│  └─ DECISIONS.md
├─ rtl/
├─ tb/
├─ constraints/
├─ scripts/
├─ reports/
└─ reference/
```

各文件职责：

- `AGENTS.md`：所有模型必须遵守的少量长期规则，例如目标器件、禁止未经允许改接口、修改后要运行哪些验证。不要放大量项目介绍。
- `PROJECT_BRIEF.md`：稳定背景，包括赛题、平台、技术路线、用户知识边界、硬件接口与演示目标。
- `MILESTONES.md`：各阶段目标、验收标准和完成状态。
- `STATUS.md`：当前可工作的版本、已经验证的功能、已知问题、最近一次测试结果。
- `HANDOFF.md`：只保存当前一次交接；下一模型完成任务后覆盖更新。
- `DECISIONS.md`：记录重要设计决定及理由，例如选择 DVP/RGB 摄像头、边界填充方式、像素位宽、阈值算法。
- `reports/`：保存综合、时序、资源和仿真报告；不要只把关键数据留在聊天中。

`PROJECT_BRIEF.md` 和 `DECISIONS.md` 是长期事实，`STATUS.md` 和 `HANDOFF.md` 是短期状态。不要每次把全部聊天记录交给 Astra。

## 五、不同模型的互动方式

### 1. 开始一个里程碑

由 Sol 主线会话读取：

- `AGENTS.md`
- `PROJECT_BRIEF.md`
- `MILESTONES.md`
- `STATUS.md`
- 当前 `HANDOFF.md`

Sol 给出本轮计划、将修改的文件和验收方法。用户确认方向后再开始实现。

### 2. 用户跟随操作

遇到安装、菜单、烧录、接线或基础概念问题时，切到“操作教练”对话：

```text
当前正在执行 M0/M1 的第 X 步。请只负责带我完成操作，不修改总体架构。
先解释这一步的目的，再一次只给 1～3 个操作。等我返回截图或日志后继续。
如果发现问题涉及接口设计、时钟域或多个 RTL 模块，请停止猜测并建议升级给主线工程师或 Astra。
```

操作完成后，把真实结果写入 `STATUS.md` 或交回主线会话，不要只说“应该成功”。

### 3. Sol 日常构建

```text
你是“星眸”项目的主线工程师。先读取 AGENTS.md、PROJECT_BRIEF.md、STATUS.md 和 HANDOFF.md。
本次只完成【里程碑/任务名称】。先列出接口、将修改的文件和验收条件，再实施。
不要顺带重构无关模块；保留已经验证的接口。完成后运行可用的仿真/检查，说明证据，并更新 STATUS.md 和 HANDOFF.md。
```

### 4. 升级给 Astra

```text
你是“星眸”项目的总架构师/疑难专家。本次问题是【问题名称】。
先读取 AGENTS.md、PROJECT_BRIEF.md、STATUS.md、HANDOFF.md，以及 HANDOFF.md 指向的相关源码和报告；不要无差别读取全部资料。

目标：【可验证目标】
允许修改：【文件或模块范围】
禁止修改：【已验证接口、管脚、分辨率等】
完成条件：【仿真、综合、时序或上板现象】

请先判断根因和方案，再实施或给主线工程师明确的接口方案。若实施，请持续到完成条件满足，或明确报告无法继续所缺少的真实信息。最后更新 DECISIONS.md（如有架构决定）、STATUS.md 和 HANDOFF.md。
```

### 5. Astra 完成后交还 Sol

Sol 不应重新猜测 Astra 的设计意图，而应先读取 Astra 更新后的 `DECISIONS.md`、`STATUS.md` 和 `HANDOFF.md`，然后继续实现、清理或扩展。

## 七、版本控制与写入规则

1. 将实际工程初始化为 Git 仓库。
2. 每个可验证里程碑完成后提交一次，例如 `M1-video-passthrough-verified`。
3. Astra 接管复杂修改前先保留一个可回退提交。
4. 初期不要让 Sol 和 Astra并行修改同一工程；用户熟悉 Git 后，才考虑用独立分支或 worktree 并行。
5. 只有经过仿真、综合或上板验证的提交才能合入稳定主线。
6. 大型生成文件和临时缓存可以忽略，但关键报告、约束、脚本和复现问题所需的小型测试数据应保留。

## 八、每个任务的验收闭环

所有模型都必须按以下闭环工作：

1. 明确目标和不允许改变的内容；
2. 说明准备修改哪些文件；
3. 完成最小实现；
4. 进行仿真/综合/静态检查；
5. 用户完成需要真实硬件的上板验证；
6. 记录证据与已知问题；
7. 更新 `STATUS.md` 和 `HANDOFF.md`；
8. 验证通过后提交版本并进入下一个里程碑。

## 九、立即执行顺序

1. 新建独立项目“嵌赛2026｜星眸FPGA”。
2. 将易灵思 2026 选题指南、VF-Ti60F225 板卡资料、原理图、管脚表、摄像头资料和参考工程放入项目来源。
3. 在实际工程目录建立上述文件结构并初始化 Git。
4. 先用 Sol 填写 `PROJECT_BRIEF.md`、`MILESTONES.md` 和精简的 `AGENTS.md`。
5. 用 Astra 对 P0 总体架构做一次审查，冻结第一版模块接口。
6. 回到操作教练 + Sol，从 M0 开发环境和点灯开始推进。
7. 每完成一个里程碑，再让 Astra做一次阶段审查；没有触发升级条件时，不需要频繁切换。

## 十、最终结论

应当规定统一交接模板，但真正保证交接可靠的不是模板本身，而是：

- 同一套真实工程文件；
- 精简、持久的项目规则；
- 可更新的当前状态；
- 明确的修改边界；
- 仿真、综合和上板证据；
- 单一写入者与可回退的 Git 版本。

模型之间采用“文件化、顺序式交接”，比让多个对话各自依赖聊天记忆更可靠。
